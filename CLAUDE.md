# Project standards — senior-level analytics portfolio

These rules apply to every phase. If a task conflicts with them, flag it rather than silently breaking them.

## Honesty and data
- Use real public data. Any synthetic or simulated data must be generated by a script in the repo, marked "SYNTHETIC" in table/file names, and listed in data/README.md with the reason it was needed.
- Never invent numbers. Every figure in the README, reports or model card must come from code that was run and can be re-run.
- Business value is always an estimate under stated assumptions, never an "achieved saving". Put every assumption (costs, rates, elasticities) in a config file and show a sensitivity analysis on the ones that matter.

## Required deliverables
1. Business case (docs/business_case.md): the decision the model improves, who makes it, current/baseline approach, and the cost of each type of error.
2. Statistical reasoning (docs/methodology.md): why each model was chosen, its assumptions, how assumptions were checked, and where it can fail.
3. Validation: out-of-time testing where the data has a time dimension. If it doesn't, say so explicitly and explain the substitute (grouped CV, holdout, bootstrap). Always include simple baselines. Write explicit leakage checks as tests.
4. Model comparison: metrics suited to the problem (not accuracy alone), uncertainty (bootstrap CIs or prediction intervals), calibration, and segment-level performance with segment sizes shown.
5. Deployment: a repeatable scoring pipeline, API or scheduled workflow, with automated tests and a one-command run.
6. Business recommendations (reports/recommendations.md): what to do, quantified with transparent assumptions, with risks and what would change the recommendation.
7. Technical documentation: data lineage (raw → final, with row counts at each step), limitations, monitoring plan, reproducibility (pinned dependencies, seeds, data versions), and a "how to run this" guide another analyst can follow. Also a model card (docs/model_card.md).

## Engineering
- Python 3.11, dependencies pinned (pyproject.toml + lock file).
- Logic in src/ as importable modules; notebooks only for narrative and they import from src/.
- pytest for transforms, leakage checks, metrics and pipeline outputs; ruff for linting; type hints.
- Config in YAML, no magic numbers buried in code. Fixed random seeds.
- Makefile or CLI that reproduces everything from raw data.
- GitHub Actions CI running lint and tests (use small fixtures, not full data).

## Working style
- Work in phases. At the end of each phase: run the tests, then summarise what was built, key results, assumptions made, and open questions.
- Prefer simple and correct over clever. When a choice is a judgement call, note it in docs/decisions.md with the alternatives considered.

## Project addendum: marketing budget optimisation

- **Synthetic data, by necessity.** No public dataset has spend, funnel, experiment and customer-economics data
  for several businesses together with the true incremental effect of each channel. The data are therefore
  simulated (D-001). Every generated table and file name contains `synthetic`. Findings demonstrate that the
  method works; they are not facts about a real company. The executive memo says so on page 1.
- **The ground truth is sealed.** `configs/ground_truth_SYNTHETIC.yaml` may be read only by
  `src/marketing_budget/synthetic/` (the generator) and `src/marketing_budget/validation/` (scoring models
  against the truth). A test enforces this. Models must learn from the generated data alone.
- **Average return is not marginal return.** No analysis may use average historical ROAS or CAC as the return
  on the next dollar. Attributed (platform-reported), incremental (causal) and marginal (next-dollar) returns
  are separate metrics with separate definitions (`docs/metric_definitions.md`).
- **Label the evidence.** Every result is tagged *causal* (randomised experiment or designed holdout),
  *model-based* (fitted on observational data, depends on assumptions) or *assumption* (a finance or
  management input). Never present a model-based result as causal.
- **Commercial framing.** Every report opens with the same six parts, in plain language: the business
  question; why it matters commercially; what the analysis establishes; what it means in business terms; the
  action management should consider; the assumptions and limitations management must understand. Statistical
  terms are explained the first time they appear in a report.
- **Challenge, don't agree.** Where the brief or a stakeholder position rests on an unsupported assumption,
  say so and state what evidence would settle it.
- **LLM output is never a source.** The AI reporting workflow (phase 7) may only restate metrics present in
  validated SQL outputs, must cite the source row for each number, may not make causal claims unless the
  metric is tagged causal, and every draft needs human sign-off.
